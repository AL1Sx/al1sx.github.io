DeepSeek Harness 安装与排错

celestia2026/9/11大约 6 分钟工具AI开发DeepSeekDSHnpm排错

记述了 DeepSeek Harness 的安装、升级还原与两类常见故障的排查方法。

DeepSeek Harness 安装与排错

约定

下面的命令以 Windows + PowerShell 为准。DSH 主目录记为 $DSH_HOME，默认是 %USERPROFILE%\.dsh，可以用同名环境变量覆盖。

官网：DeepSeek Harness

使用工具

  • Node.js: dsh 本身就是 Node 应用，靠它来跑。建议 22 以上——本文最后的会话日志解压要用到 Node 内置 zlib 的 zstd 接口，它在 22.15 才加入。

  • npm: 用来全局安装和升级 dsh。

  • git: 一部分插件依赖直接从 git 拉取，装上省事。

注

DeepSeek Harness 官网
Node.js 下载
npm 文档

安装

确认包

npm view @deepseek-ai/dsh version

全局安装

npm install -g @deepseek-ai/dsh

验证

dsh --version
dsh web --help

dsh --version 打印的是 dsh 自己的版本，dsh web --help 打印的是 web 应用自己的参数。这两个都能正常输出，基本就算装好了。

安装脚本可能被拦下

npm 11 对依赖的安装脚本默认要审批，需要原生二进制的包（比如 node-pty、koffi）可能被拦。多数包自带各平台预编译产物，先按上面的方式验证；万一功能确实缺失，再看一眼待审批清单：

npm approve-scripts --allow-scripts-pending

启动 Web UI

dsh web                 # 启动并自动打开浏览器
dsh web --no-open       # 不自动打开
dsh web --port 8080     # 指定端口

启动器只解析自己的 flag，它不认识的第一个 token 之后全部交给应用，所以 --no-open、--port 属于 web 应用。想看启动器的参数用 dsh --help，看应用的用 dsh web --help。

升级前备份与还原

升级前先把 $DSH_HOME 备份一份。profiles\node_modules 可以排除掉：体积大，而且它可以用 pnpm 装回来（dsh plugin --profile <名字> install 会把参数原样转发给 pnpm）。

robocopy "$env:USERPROFILE\.dsh" "$env:USERPROFILE\dsh-backup-$(Get-Date -Format 'yyyyMMdd-HHmmss')" /E /XD node_modules

顺手在备份目录里留一份说明，记下备份时间、版本和还原命令，以后不用靠回忆：

dsh 升级前备份
创建时间: <时间>
来源: %USERPROFILE%\.dsh
升级前版本: <旧版本>
目标版本: <新版本>
已排除: profiles\node_modules（可用 pnpm 重装）

完整还原命令:
  Copy-Item '<备份目录>\*' "$env:USERPROFILE\.dsh\" -Recurse -Force

还原分两步：先给当前状态拍个快照，再把备份覆盖回去。这样万一备份本身有问题，也还有退路。

# 1) 当前状态的安全快照
robocopy "$env:USERPROFILE\.dsh" "$env:USERPROFILE\dsh-before-restore-$(Get-Date -Format 'yyyyMMdd-HHmmss')" /E /XD node_modules

# 2) 还原（合并覆盖，不会动现有的 node_modules）
Copy-Item '<备份目录>\*' "$env:USERPROFILE\.dsh\" -Recurse -Force

还原完检查 $DSH_HOME 下的 settings.yaml、profiles\<profile>\cordis.patch.yml、skills、sessions、storages 是否都回来了。node_modules 保持原样就行，不用重装。

排错 A：插件加载失败

现象：dsh web 刚起来就退出，报 plugin tree failed to load，后面跟着 Cannot find module '...\xxx.mjs?v=1' 这类找不到模块的错误。

原因：cordis.patch.yml 里插件的 name 带了缓存参数 ?v=1。?v= 这种写法在浏览器资源和打包器里很常见，用来绕开缓存；但在 dsh 的 patch 层里，name 必须是模块标识符——要么是包名，要么是指向模块文件的路径，不支持查询串。

修复：把补丁层里的查询参数去掉。profile 自己的用户层是 profiles\<profile>\cordis.patch.yml，home 级还有 $DSH_HOME\cordis.patch.yml（存在的话），两处都看一眼。

# profiles/<profile>/cordis.patch.yml
- insert:
    - id: <插件id>
      name: ./<插件>.mjs          # 原来可能是 ./<插件>.mjs?v=1

去掉查询串之后还是找不到模块

那就不是缓存参数的问题了，先核对文件名大小写、扩展名和相对位置是否和 name 一致——Windows 上大小写不敏感，换到别处就可能出错。dsh 的报错会带上出错条目的 id 与 name（failed to load loader entry <id> (<name>): ...），照着核对即可。

改完重启 dsh web。想先确认配置树有没有被正确读到，可以不启动直接导出：

dsh web --dump-config

排错 B：发消息没反应

现象：Web UI 能正常打开，后端也没有明显报错，但发出去的消息回复是空的，token 用量一直是 0。

第一步，从会话日志里挖出真实错误。 前端看不到，日志里其实记着。位置是 $DSH_HOME\sessions\<工作目录>\<会话id>\session.v3.jsonl.zstd。路径里的工作目录经过转义：路径分隔符（: 和 \）都换成 -，首尾各补一个 --。例如工作目录是 D:\projects\demo，对应的目录名就是 --D-projects-demo--。

这份日志是多帧追加的 zstd，直接解压只能拿到第一帧，必须逐帧解：

node -e "const fs=require('fs'),z=require('zlib');const b=fs.readFileSync(process.argv[1]);const m=Buffer.from([0x28,0xB5,0x2F,0xFD]);let o=[],i=0;while((i=b.indexOf(m,i))!==-1){o.push(i);i+=4}const p=[];for(let k=0;k<o.length;k++){const e=k+1<o.length?o[k+1]:b.length;try{p.push(z.zstdDecompressSync(b.subarray(o[k],e)))}catch(x){p.push(Buffer.from(''))}}const r=Buffer.concat(p);fs.writeFileSync(process.argv[2],r);console.log('frames',o.length,'bytes',r.length)" '<会话>\session.v3.jsonl.zstd' out.jsonl

嫌找路径麻烦的话，直接取最近改动的那个：

Get-ChildItem -Recurse -Filter 'session.v3.jsonl.zstd' "$env:USERPROFILE\.dsh\sessions" |
  Sort-Object LastWriteTime -Descending | Select-Object -First 1 -ExpandProperty FullName

然后在 out.jsonl 里搜 REQUEST_EXTENSION（直接搜 must declare non-empty name and version 更快命中），会看到形如这样的记录：

DeepSeek request extension preparation failed  code: REQUEST_EXTENSION

第二步，定位根因。 这个错误来自请求扩展注册表（dsh_plugin_packages）：它会为每个激活的插件条目解析所属包的 package.json，而且要求 name 和 version 都非空。对相对路径插件（./<插件>.mjs），它会从模块所在目录逐级往上找最近的 package.json——找到的正是 profile 自己的那个。

这里有个坑：dsh 自动生成的 profile package.json 默认只有 name、没有 version，官方文档里的最小示例也是这样。所以只要这个 profile 用过任何相对路径插件，准备阶段就会直接抛错。日志里伴随的原始 cause 长这样：

plugin-package-inventory-deepseek: <路径>\profiles\<profile>\package.json must declare non-empty name and version

修复：给 profile 的 package.json 补上 version，其它内容别动。

{
  "name": "dsh-profile-web",
  "version": "0.0.0",
  "private": true,
  "dsh": {
    "profile": {
      "bundles": [
        "@deepseek-ai/dsh-base",
        "@deepseek-ai/dsh-web-app"
      ],
      "patchReload": "live"
    }
  }
}

改完启动，stderr 干净了，再发一条消息确认能正常返回。

排错小抄

现象常见原因处理
启动即退，Cannot find module ...mjs?v=1插件 name 带了 ?v= 这类查询串去掉查询参数
能启动但没回复、token 为 0请求扩展准备失败会话日志里查 REQUEST_EXTENSION，给 profile 的 package.json 补 version
原生模块功能异常安装脚本被 npm 拦下npm approve-scripts --allow-scripts-pending
升级后配置丢失没有还原备份先快照当前状态，再 Copy-Item 还原（保留 node_modules）

这两个坑我都踩过一遍，回头看其实都是很小的地方：一个多余的查询参数，一个缺失的版本号。真出问题时别急着重装，先把日志里的真实错误挖出来，答案往往就写在里面。
